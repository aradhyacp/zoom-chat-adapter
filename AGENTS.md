# AGENTS.md

Guidance for AI coding agents working with **`zoom-chat-adapter`** — whether you are
consuming it from npm in someone else's project, or editing this repository itself.

Read the "Using the package" sections if you are wiring this adapter into an
application. Read "Working in this repo" only if you are changing the adapter's own
source.

---

## What this package is

`zoom-chat-adapter` is a **Zoom Team Chat adapter for [Chat SDK](https://chat-sdk.dev)**.
It lets a bot receive and send Zoom Team Chat messages — channel messages, DMs, slash
commands, and @-mentions — through the same `Chat` interface used by other Chat SDK
adapters.

It is a **community-maintained** package. It is **not** an official `@chat-adapter/*`
package, and it is not published or supported by Zoom. Do not describe it as official.

| | |
|---|---|
| npm package | [`zoom-chat-adapter`](https://www.npmjs.com/package/zoom-chat-adapter) |
| Source | [github.com/aradhyacp/zoom-chat-adapter](https://github.com/aradhyacp/zoom-chat-adapter) |
| Issues | [github.com/aradhyacp/zoom-chat-adapter/issues](https://github.com/aradhyacp/zoom-chat-adapter/issues) |
| License | MIT |
| Format | ESM only (`"type": "module"`) — no CommonJS build |
| Runtime | Node.js. Uses `node:crypto` and the global `fetch`/`Request`/`Response` Web APIs |

### Where the source comes from

The published npm tarball ships **only the `dist/` directory** (see `files` in
`package.json`). `dist/` is generated by [tsup](https://tsup.egoist.dev/) from `src/`
and is **not** checked into git.

That means:

- Consumers get `dist/index.js` (ESM) plus `dist/index.d.ts` (types). There is no
  bundled source and no source map in the published package.
- To read or change the real implementation, go to the GitHub repository and read
  `src/`, not `node_modules/zoom-chat-adapter/dist/`.
- Never hand-edit files under `node_modules/zoom-chat-adapter/` to fix a bug. Edits
  there are wiped on the next install. Open an issue or a PR against `src/` instead.

## Using the package

### Install

```bash
pnpm add zoom-chat-adapter chat @chat-adapter/state-memory
```

`chat` is a regular `dependency` of this package, so a package manager pulls it in
automatically — install it explicitly anyway, since your application imports `Chat`
from it directly. `@chat-adapter/state-memory` is not a dependency of this package,
so install it explicitly too: your application imports `createMemoryState` from it
directly, and depending on a transitive package is fragile.

### Minimal usage

```typescript
import { createMemoryState } from "@chat-adapter/state-memory";
import { Chat } from "chat";
import { createZoomAdapter } from "zoom-chat-adapter";

const bot = new Chat({
  userName: "mybot",
  adapters: {
    zoom: createZoomAdapter(),
  },
  state: createMemoryState(),
});

bot.onNewMention(async (thread, message) => {
  await thread.post("Hello from Zoom!");
});
```

Called with no arguments, `createZoomAdapter()` reads every credential from environment
variables.

### Wiring the webhook

Zoom delivers everything over a single HTTP endpoint. Hand the raw `Request` straight to
`handleWebhook` — do **not** parse the body first (see "Common mistakes" below).

```typescript
// app/api/webhooks/zoom/route.ts
import { after } from "next/server";
import { bot } from "@/lib/bot";

export async function POST(request: Request) {
  return bot.webhooks.zoom(request, { waitUntil: after });
}
```

`handleWebhook` returns a `Response` you should return as-is:

| Situation | Response |
|---|---|
| Body is not valid JSON | `400 Invalid JSON` |
| `endpoint.url_validation` (CRC challenge) | `200` with `{ plainToken, encryptedToken }` |
| Missing/stale/mismatched signature | `401 Invalid signature` |
| Handled or unrecognised event | `200 ok` |

Passing `waitUntil` (e.g. Next.js `after`, or a Cloudflare `ExecutionContext.waitUntil`)
makes event processing happen after the response is sent, so Zoom is not kept waiting.
Without it, `handleWebhook` awaits processing before responding.

### Configuration

Every option falls back to an environment variable. All of them except `userName`,
`markdownSupport`, and `logger` are **required at runtime** — `createZoomAdapter()` throws
a `ValidationError` from `@chat-adapter/shared` at construction time if one is missing.

| Option | Env var | Required | Notes |
|---|---|---|---|
| `clientId` | `ZOOM_CLIENT_ID` | Yes | S2S OAuth app client ID |
| `clientSecret` | `ZOOM_CLIENT_SECRET` | Yes | S2S OAuth app client secret |
| `accountId` | `ZOOM_ACCOUNT_ID` | Yes | Sent on message API calls; not sent in the token request |
| `robotJid` | `ZOOM_ROBOT_JID` | Yes | Bot JID from Team Chat Subscription |
| `webhookSecretToken` | `ZOOM_WEBHOOK_SECRET_TOKEN` | Yes | Used for HMAC signature + CRC |
| `userName` | `ZOOM_BOT_USERNAME` | No | Defaults to `"zoom-bot"` |
| `markdownSupport` | `ZOOM_MARKDOWN_SUPPORT` | No | Defaults to `true`. Sends `is_markdown_support: true` and a Markdown body |
| `logger` | — | No | Defaults to `new ConsoleLogger("info").child("zoom")` |

Explicit config takes precedence over the environment:

```typescript
createZoomAdapter({
  clientId: "your-client-id",
  clientSecret: "your-client-secret",
  accountId: "your-account-id",
  robotJid: "bot-jid@xmpp.zoom.us",
  webhookSecretToken: "your-secret-token",
});
```

Zoom Marketplace app setup, the required scopes, and the ngrok flow are documented in
[README.md](./README.md). Do not re-derive those steps — point users there.

## API surface

Exported from the package root:

- `createZoomAdapter(config?)` — the factory. **Prefer this** over the class; it does the
  env-var resolution and validation.
- `ZoomAdapter` — the class. Only construct it directly if you are supplying a fully
  resolved internal config.
- Types: `ZoomAdapterConfig`, `ZoomThreadId`, `ZoomMessageWithReply`,
  `ZoomWebhookPayload`, `ZoomCrcPayload`, `ZoomBotNotificationPayload`,
  `ZoomAppMentionPayload`.

### What is implemented

| Capability | Status |
|---|---|
| `handleWebhook` | Implemented — CRC, signature verification, event dispatch |
| `postMessage` | Implemented |
| `editMessage` | Implemented |
| `deleteMessage` | Implemented |
| Threaded replies | Implemented via `metadata.replyTo` |
| `startTyping` | Silent no-op — Zoom has no typing-indicator API |
| `fetchMessages` | **Throws `NotImplementedError`** |
| `fetchThread` | **Throws `NotImplementedError`** |
| `addReaction` / `removeReaction` | **Throws `NotImplementedError`** |
| `parseMessage` | **Throws `NotImplementedError`** |

Do not write code that calls the `NotImplementedError` methods and do not suggest them to
users as if they work. If a user needs message history or reactions, say plainly that this
adapter does not implement them yet.

### Threaded replies

`postMessage` accepts the standard `AdapterPostableMessage`, but it also recognises a
Zoom-specific shape for replies:

```typescript
await adapter.postMessage(threadId, {
  raw: "Reply text",
  metadata: { replyTo: "parent-message-id" },
});
```

`metadata.replyTo` becomes `reply_main_message_id` on the Zoom API call. Note the caveat
under Limitations: replies posted into a **DM** thread will send, but Zoom will never
deliver a webhook for replies the user makes back in that thread.

### Thread IDs

```
zoom:{channelId}:{messageId}
```

`channelId` is a JID. The suffix is what distinguishes a channel from a DM — this is the
only DM-detection mechanism the adapter has:

- `…@conference.xmpp.zoom.us` → **channel**
- anything else (a user JID) → **DM**

`messageId` is the `event_ts` for `bot_notification`, or the message UUID for
`team_chat.app_mention`. `decodeThreadId` tolerates a channel-level ID with no
`messageId` (`zoom:{channelId}`), returning `messageId: ""`. It throws a `ValidationError`
if the string does not start with `zoom:` or has an empty `channelId`.

### Authentication

The adapter fetches a Server-to-Server OAuth token with the **`client_credentials`**
grant and caches it in memory, refreshing 60 seconds before expiry. A failed token fetch
throws an `AuthenticationError`. The cache lives on the adapter instance, so a long-lived
instance is preferable to constructing a new one per request.

### Formatting

Messages are sent with Zoom's Markdown parser enabled by default (`is_markdown_support:
true`), because the structured `style` API only supports bold and italic. The converter
maps the AST to Zoom's dialect:

- `**bold**` → Zoom's `*bold*` (the chatbot parser uses the legacy single-asterisk
  form; `**…**` renders as plain text despite the docs table). Verified live:
  `*x*` and `***x***` are bold, `**x**` is plain.
- `_italic_`, `` `code` ``, `~strikethrough~` — native Zoom tokens
- `> quote` — block quote
- links — `label <https://url>` (Zoom documents only the bare `<url>` form)
- images — `<img:url|alt>`
- headings — bold line (Zoom has no heading token)
- lists — real `•` bullets (Zoom has no list token)
- tables — pipe-separated text rows (Zoom has no table token)
- `__underline__` — plain text; **Zoom has no underline token**

Code spans and fences are protected from the Zoom-token regexes, so code that merely
looks like `~strike~` or `__underline__` is left alone. Empty messages are skipped rather
than sent, because the Zoom API rejects them.

`{ ast }` postables are passed straight to `toZoomContentBody`; they must not go through
`renderPostable` first. Serializing an AST to the Zoom dialect and re-parsing that string
would turn bold into italic, because `*x*` is emphasis in standard Markdown. The
`toAstFromPostable()` helper is the one place that distinction lives.

Setting `markdownSupport: false` (or `ZOOM_MARKDOWN_SUPPORT=false`) falls back to
structured segments with whole-paragraph bold only; links, strikethrough, quotes and images
keep their text but lose their formatting.

## Common mistakes to avoid

These are the failure modes most likely to come up. Check for them before suggesting a fix
elsewhere.

1. **Consuming the request body before `handleWebhook`.** A Web `Request` body can only be
   read once, and the HMAC is computed over the exact raw bytes. Calling `request.json()`
   in middleware or a logger will break signature verification for every event. Pass the
   untouched `Request`.
2. **Reaching into `node_modules/zoom-chat-adapter/dist/`.** That is build output. Change
   `src/` in the GitHub repo.
3. **Assuming `thread.subscribe()` works.** It does not — see Limitations.
4. **Using the `account_credentials` grant.** The `/v2/im/chat/messages` endpoints need a
   `client_credentials` token. The wrong grant surfaces as a `401`.
5. **Expecting CommonJS.** ESM only. `require("zoom-chat-adapter")` will not work.
6. **Treating a missing credential as a runtime bug.** `createZoomAdapter()` throws
   immediately with a message naming the exact env var to set.

## Known limitations

State these plainly rather than attempting workarounds — the first two are confirmed Zoom
platform behaviour and cannot be fixed in this adapter.

- **Thread subscription does not work.** Every `bot_notification` arrives with a thread ID
  derived from a unique `event_ts`, and Zoom supplies no `reply_to` / `parent_message_id`
  to correlate replies with the original message. Consecutive messages in what the user
  sees as one conversation cannot be linked.
- **DM thread replies are never delivered.** Zoom does not fire `chat_message.replied` for
  1:1 DM thread replies.
  ([devforum thread](https://devforum.zoom.us/t/clarification-on-zoom-chatbot-webhook-events-for-thread-replies-in-1-1-chats/134812))
- **Unicode HMAC bug (ZOOM-506645).** Zoom's servers may normalise emoji and accented
  characters differently before signing, so such payloads can fail verification. The
  adapter logs the first 200 bytes of the body as hex at `debug` level when the comparison
  fails. Affected users should contact Zoom Support citing ZOOM-506645.
- **Streaming is buffered,** not incremental — output accumulates and is sent as one
  message.
- **Images render only from Zoom-trusted domains.** The Zoom client drops images from
  other hosts (Unsplash included) with a `[Security] Blocked image from untrusted domain`
  console warning. The adapter sends the documented `<img:url|alt>` token correctly; the
  host must be on the app's trusted-domain list (or one Zoom already trusts, such as
  `developers.zoom.us`).
- **No reactions, no message history, no typing indicator.**

## Working in this repo

Only relevant when editing the adapter's own source.

### Layout

```
src/index.ts      ZoomAdapter class + createZoomAdapter factory
src/markdown.ts   ZoomFormatConverter — Chat SDK markdown ⇄ Zoom Markdown / segments
src/types.ts      Config and webhook payload types
src/*.test.ts     Vitest suites, colocated with source
```

### Commands

```bash
pnpm test        # vitest run --coverage
pnpm test:watch  # vitest
pnpm typecheck   # tsc --noEmit
pnpm check       # ultracite check  (lint, no writes)
pnpm fix         # ultracite fix    (format + autofix)
pnpm build       # tsup → dist/
```

Run `pnpm typecheck` and `pnpm test` before claiming a change works. Note that
`tsconfig.json` excludes `**/*.test.ts`, so `pnpm typecheck` does **not** type-check the
test files — vitest surfaces those errors instead.

### Code style

Formatting and linting are handled by [Ultracite](https://www.ultracite.ai/) (a
[Biome](https://biomejs.dev/) preset) via `biome.jsonc`. Run `pnpm fix` rather than
hand-formatting, and let the tool settle mechanical questions — notably object keys are
sorted alphabetically and large numeric literals take `_` separators.

Beyond what Biome enforces, this codebase favours:

- Explicit types on exported functions; `unknown` over `any`.
- Early returns over nested conditionals.
- Named constants over magic numbers.
- `Error` subclasses from `@chat-adapter/shared` (`ValidationError`,
  `AuthenticationError`) and `NotImplementedError` from `chat`, with a message that names
  the adapter and the operation.
- Comments that explain *why* — particularly the ones recording Zoom platform quirks.
  Preserve those; they encode findings that are expensive to rediscover.
- A `biome-ignore` comment must carry a real justification, not a restatement of the rule.

### Pre-commit hook

A Husky `pre-commit` hook (`.husky/pre-commit`) runs `ultracite fix` on staged files,
re-stages them, then runs `ultracite check` and **blocks the commit** if lint errors
remain. If a staged file also has unstaged changes, the hook deliberately leaves its fixes
unstaged and prints the filename — review and stage those yourself rather than bypassing
the hook.

The hook does **not** run tests or typecheck. Run those yourself before committing.

### Publishing

`dist/` is gitignored and built by `pnpm build`. Bump the version in `package.json`, build,
and publish — `files: ["dist"]` and `publishConfig.access: "public"` are already set.
